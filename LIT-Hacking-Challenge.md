### LIT Hacking Challenge

#### Our Security Hypothesis

We hypothesize that the direct connection between a LIT client and the LIT test server is resistant to Man-in-the-Middle (MitM) and Adversary-in-the-Middle (AiTM) attacks.

The purpose of this challenge is to independently evaluate this hypothesis and identify practical methods of bypassing the intended mutual TLS (mTLS) protections. Test evidence and submitted findings will be retained to support evaluation of the hypothesis.

The LIT test server uses mTLS to authenticate the client at the transport layer. The client must prove possession of the private key associated with its registered LiveKey. The private key is not transmitted to the server and is not intended to be exportable from the protected client environment.

We invite security researchers, ethical hackers, students, and other security enthusiasts to test, challenge, and attempt to disprove this hypothesis.

#### The Target

The **LIT test server is a synthetic Service Provider** created specifically for demonstration and authorized security testing. It exposes a synthetic **User Tasks** service through a direct mTLS-protected connection.

Each test user has an independent task list containing synthetic test data only. The service does not contain production data, customer information, or confidential business information.

The challenge environment is hosted on an Amazon EC2 instance owned and operated by WinMagic specifically for this challenge. AWS infrastructure and AWS-managed services are not part of the challenge scope. Testing is limited to the LIT Service Provider and associated challenge assets.

The objective is to determine whether an attacker can defeat the mTLS protection and modify a target test user's task list without possessing or legitimately using that user's LiveKey private key.

Client registration is performed through a separate, intentionally unprotected REST API provided solely to simplify challenge setup and onboarding. Participants may use this API to register clients and keys associated with their own test accounts. The registration process is not considered a security boundary and is not part of the challenge scope.

The challenge begins only after the client's key has been created, its public key has been registered with the Service Provider, and the corresponding client certificate has been issued and installed.

#### What Counts as a Successful Attack?

A successful attack must demonstrate that a participant can:

- Intercept, relay, redirect, or otherwise manipulate the connection between a legitimate LIT client and the LIT test server
- Use the attack to modify a target test user's task list without possessing or legitimately using that user's LiveKey private key
- Perform the attack using only test accounts, devices, and networks that the participant owns, controls, or is explicitly authorized to use

To exercise this objective without targeting another person, a participant may use multiple test accounts under their own control, with one account acting as the legitimate client and another acting as the target account.

The result must be reproducible and must demonstrate that the protection was bypassed through the client-to-server connection.

Finding a user-interface issue, modifying only the attacker's own task list, attacking the registration API, or obtaining access by changing the Service Provider or legitimate client configuration does not, by itself, constitute a successful attack.

#### Challenge Scope and Assumptions

This challenge evaluates the direct mTLS-protected connection between the LIT client and the synthetic LIT Service Provider.

The challenge assumes that the attacker can operate from a network they own, control, or are explicitly authorized to use, and can observe, intercept, relay, redirect, replay, or otherwise manipulate traffic generated by their own challenge client and test accounts. The attacker may operate as a MitM or AiTM between those authorized assets and the LIT test server.

The legitimate client device, operating system, and LIT client software are assumed to remain trusted and uncompromised throughout the attack. A valid attack must therefore succeed without:

- Physical access to the legitimate client device during the attack
- Installing malware, agents, browser extensions, hooks, proxies, debuggers, monitoring tools, or other attack software on the legitimate client device
- Modifying the LIT client software
- Modifying the legitimate client operating system or its configuration to weaken, disable, or redirect certificate handling
- Extracting certificates, private keys, credentials, or other secrets from the legitimate client device through local access
- Taking control of another person's Windows or application session
- Social-engineering another person into assisting with the attack

The following activities are within scope when performed only against a participant's own authorized challenge assets:

- MitM and AiTM attacks
- TLS interception or relay
- Client-certificate substitution or misuse
- Attempts to authenticate without possession of the registered private key
- Attempts to redirect an authorized LIT client to an attacker-controlled service
- Attempts to modify the target task list by bypassing the mTLS protection

The following activities are outside scope:

- Attacks against client registration, key creation, certificate enrollment, or certificate issuance
- Abuse or modification of registration data through the unprotected registration REST API
- Attacks against AWS infrastructure or AWS-managed services
- Attacks against production systems or unrelated infrastructure
- Attacks against another participant's accounts, devices, networks, traffic, or testing environment
- Physical attacks against devices
- Destructive testing
- Installation of attack software on another person's or participant's device
- Modification of another person's client device, operating system, browser, or LIT client software
- Unauthorized access to, modification of, or deletion of another participant's environment

A successful submission must demonstrate that the attacker can defeat the intended mTLS protection and modify the target account's synthetic task list while operating solely from an authorized network and without compromising, controlling, or modifying the legitimate client device.

Attacks involving endpoint compromise, malware, physical access, local key extraction, operating-system modification, reverse engineering, or client-side instrumentation may be valuable research, but they are outside this challenge and will not be considered successful challenge submissions.

##### Install the LiveKey Engine Service

1. Copy `LiveKeyEngine.exe` to:

   ```text
   C:\Windows\System32
   ```

2. Launch Windows Command Prompt as Administrator.

3. Create and start the service:

   ```cmd
   sc.exe create LiveKeyEngine binPath= "C:\Windows\System32\LiveKeyEngine.exe" start= auto
   sc.exe start LiveKeyEngine
   ```

##### Install and Register the WinMagic CNG Key Storage Provider

1. Copy `WmKsp.dll` to:

   ```text
   C:\Windows\System32
   ```

2. In an elevated command prompt, run:

   ```cmd
   rundll32 "C:\Windows\System32\WmKsp.dll" Register
   ```

#### Key Creation and Certificate Enrollment

After the WinMagic LiveKey Engine service and WinMagic CNG Key Storage Provider have been installed and registered, a LiveKey-backed cryptographic key will be created at the next Windows user logon.

The client will then automatically generate a certificate request and submit it to the Test server. If the request is accepted, the server will issue a client certificate. The certificate will be installed in the user's Windows certificate store and associated with the newly created key.

This enrollment process exists solely to establish the initial trust relationship between the client and the Service Provider. Client registration, key creation, certificate enrollment, certificate issuance, and certificate installation are not challenge targets.

Participants must begin attack attempts only after:

- The LiveKey Engine service has been installed and started
- The WinMagic CNG Key Storage Provider has been registered
- The user has completed a Windows logon
- The client key has been created
- The certificate request has been submitted
- The client certificate has been issued and installed
- The client's public key has been registered with the Service Provider

The challenge evaluates the mTLS-protected connection after successful enrollment and registration have already occurred.

#### Removing Challenge Software

Perform these steps from an elevated Windows Command Prompt.

1. Stop and delete the LiveKey Engine service:

   ```cmd
   sc.exe stop LiveKeyEngine
   sc.exe delete LiveKeyEngine
   ```

2. Unregister the WinMagic CNG Key Storage Provider:

   ```cmd
   rundll32 "C:\Windows\System32\WmKsp.dll" Unregister
   ```

3. After the service has stopped and the provider has been unregistered, remove the installed challenge binaries:

   ```cmd
   del "C:\Windows\System32\LiveKeyEngine.exe"
   del "C:\Windows\System32\WmKsp.dll"
   ```

4. Remove challenge certificates and keys only from the dedicated test environment and only if you can positively identify them as challenge artifacts.

If a component cannot be removed cleanly, stop and restore the virtual-machine snapshot or test-system backup created before installation.
